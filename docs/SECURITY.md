# Безопасность Sunnet

Безопасность заложена в фундамент, а не добавлена сверху. Ниже — что защищено уже сейчас, как именно, и чего прототип пока не делает.

## Аккаунты и вход

| Угроза | Защита | Где в коде |
| --- | --- | --- |
| Утечка базы → пароли | scrypt (N=2¹⁵, r=8, p=1) с солью, автоматический перехэш при усилении параметров | `server/src/lib/crypto.ts` |
| Утечка базы → вход по сеансу | В базе только SHA-256 от 256-битного токена сеанса | `modules/auth/sessions.ts` |

Лимиты по аккаунту, а не по IP: 2 кода входа за 30 минут, повтор — один раз через 30 секунд, сброс — 4 раза в час. В чате Sunnet рядом с кодом — система, браузер и IP того, кто входит | `modules/auth/flow-store.ts`, `flow.service.ts` |

| Определение аккаунтов через «Забыли пароль» | Одинаковый ответ для любых логинов; письмо уходит только на подтверждённую почту | `requestPasswordReset()` |
| Захват почты другим аккаунтом | Подтверждённый адрес уникален; вход и восстановление по почте — только по подтверждённому адресу; при смене адреса уведомляется старый | `verifyEmail()`, `changeEmail()` |
| Сброс пароля по украденной почте | Нужны два кода: из письма и из чата Sunnet на устройстве, где человек вошёл (если активных сеансов нет — только из письма); после сброса все сеансы завершаются, в чат Sunnet и на почту приходит уведомление; TOTP после сброса всё равно спрашивается | `sendResetCodes()`, `setNewPassword()` |
| Подделка служебного чата | Писать от имени Sunnet может только сервер; в чат Sunnet нельзя писать и пересылать, его нельзя удалить или покинуть, служебного пользователя нельзя заблокировать; имя `sunnet` занято | `chats.service.ts` (`assertNotSystemChat`) |

| Оставленный разблокированным телефон | Код-пароль приложения (PBKDF2, 600 000 итераций) с автоблокировкой | `shared/lib/passcode.ts` |

## Запросы

- **CSRF:** изменяющие запросы требуют доверенный `Origin` (или совпадающий с `Host`) **и** заголовок `X-CSRF-Token`, совпадающий с cookie; токен подписан HMAC и привязан к сеансу (нельзя подставить токен из чужого сеанса). Для WebSocket тоже проверяется `Origin` (защита от CSWSH).
- **Валидация:** каждый вход проходит zod-схему; неизвестные поля отбрасываются (нет mass-assignment); из текста удаляются управляющие и bidi-символы (защита от подмены текста «Trojan Source»), сохраняя эмодзи.
- **SQL-инъекции:** только параметризованные запросы; пользовательский ввод для FTS5 и LIKE экранируется.
- **XSS:** React экранирует вывод, `dangerouslySetInnerHTML` не используется; ссылки — только `http(s)` с `rel="noopener noreferrer nofollow"`.
- **Заголовки:** CSP (`default-src 'self'`, `frame-ancestors 'none'`, `object-src 'none'`), HSTS с preload, `X-Frame-Options: DENY`, `nosniff`, COOP/CORP, `Referrer-Policy`, `Permissions-Policy`.
- **Логи:** cookies, токены и CSRF-заголовки вырезаются из логов.
- **Ограничение частоты:** глобальный лимит + отдельные лимиты на вход, 2FA, отправку сообщений, публикации, комментарии, загрузки, поиск, жалобы.

## Приватность

- Закрытый профиль с заявками на подписку; «кто может писать / комментировать / видеть время захода» (все / мои подписки / никто); отчёты о прочтении взаимны.
- Блокировка скрывает контент в обе стороны и запрещает сообщения, подписки, комментарии; «скрытие» убирает автора из лент без его ведома.
- Все решения принимает `Policy` — одна точка, которую покрывают тесты.
- **Фото сжимаются на устройстве с удалением EXIF**, включая GPS-координаты.
- Истории «для близких друзей» отсекаются на сервере (`Policy.canViewStory` и SQL-условие в ленте, профиле и «Актуальном»): посторонний получает 404, а не пустую картинку. Истёкшие истории доступны только автору и через его «Актуальное».
- Списки авторов закрытые по умолчанию; коллекции, черновики и скрытые слова видит только владелец. Скрытые слова передаются в FTS5 только как параметр запроса.
- Пригласительные ссылки — случайные токены, с необязательным сроком и лимитом вступлений, отзываются администратором.
- Экспорт своих данных и удаление аккаунта с очисткой личных данных.

## Файлы

- Тип определяется по сигнатуре содержимого, а не по расширению/заголовку; неизвестные типы отклоняются (HTML под видом картинки не пройдёт).
- Лимиты размера по типу проверяются потоково, во время загрузки.
- Файлы хранятся под случайными именами вне веб-корня; ссылки подписаны HMAC и истекают; ответы отдаются с `nosniff`, `CSP: sandbox`, `CORP: same-origin`; архивы и документы — только как вложения.
- Прикрепить к публикации или сообщению можно только свой файл.

## Звонки

- Медиа идёт напрямую между устройствами по WebRTC и всегда шифруется **DTLS-SRTP**; сервер видит только сигнализацию (SDP и ICE-кандидаты).
- Сигналы пересылаются только участникам звонка и только в тот сеанс, который принял звонок (другие вкладки и устройства собеседника их не получают); размер сообщения WebSocket ограничен.
- Позвонить можно только в личный или секретный чат; заблокировавший вас пользователь не получит вызов. Звонок без ответа завершается через 45 секунд, а при закрытии сеанса — сразу.
- STUN/TURN задаются переменными окружения (`STUN_URLS`, `TURN_URLS`, `TURN_USERNAME`, `TURN_CREDENTIAL`) и отдаются только авторизованным пользователям.

## Сквозное шифрование (секретные чаты)

1. Каждое устройство создаёт пару ключей **ECDH P-256**; приватный ключ **неизвлекаемый** (`extractable: false`) и хранится в IndexedDB — даже JavaScript страницы не может его прочитать, только использовать.
2. Публичный ключ публикуется на сервере; подменить ключ уже зарегистрированного устройства нельзя.
3. Ключ чата = **HKDF-SHA256**(ECDH-секрет, salt = id чата, info = `omni-secret-chat-v1`) → **AES-256-GCM**.
4. Каждое сообщение — со случайным 96-битным IV; id чата передаётся как AAD (шифротекст нельзя «переложить» в другой чат).
5. Сервер принимает в секретный чат только шифротекст и только с устройства, к которому привязан чат.
6. **Отпечаток ключей** (эмодзи + 60 цифр) позволяет собеседникам убедиться в отсутствии подмены (MITM).
7. Таймер самоуничтожения удаляет сообщения на сервере; расшифрованный текст хранится только в памяти вкладки.

**Ограничения текущей версии** (в [дорожной карте](ROADMAP.md)): нет forward secrecy (план — Double Ratchet / MLS для групп), секретный чат привязан к одному устройству (как в Telegram), вложения в секретных чатах пока не поддерживаются, обычные («облачные») чаты шифруются только транспортно (TLS) и на уровне диска сервера.

## Цепочка поставок

- Минимум зависимостей: криптография, TOTP, ID, база — на встроенных модулях Node.js.
- `npm audit` в CI (сейчас 0 уязвимостей), Dependabot для обновлений.
- Docker-образ: production-зависимости, непривилегированный пользователь, read-only файловая система, `no-new-privileges`, сброс capabilities.

## Тесты

`apps/server/test/flow.test.ts` проверяет вход по шагам (почта и телефон, неверный код, повтор через 30 секунд, лимит 2 кода за 30 минут и «только в чат»), сброс двумя кодами и лимит 4 в час, вход по QR (разрешение и отказ), регистрацию с подтверждением почты и отсечением эмодзи, ограничения чата Sunnet и поздравления с днём рождения. `apps/server/test/security.test.ts` проверяет: хэширование и подделку шифротекста, CSRF (отсутствие токена, чужой Origin, токен чужого сеанса), блокировку перебора без раскрытия логинов, полный цикл 2FA с защитой от повтора и одноразовостью резервных кодов, завершение сеансов при смене пароля, закрытые профили, «кто может писать», блокировки, недоступность чужих чатов, идемпотентность отправки, права в каналах, ограничения секретных чатов (только шифротекст, привязка к устройству, запрет подмены ключа), проверку типов файлов и подписей ссылок, запрет прикреплять чужие файлы.

## Перед запуском в интернете

- [ ] Длинный случайный `APP_SECRET` (`openssl rand -base64 48`), храните его вне репозитория
- [ ] HTTPS через обратный прокси, `TRUST_PROXY=1`, корректный `PUBLIC_ORIGIN`
- [ ] Резервные копии: внешнее хранилище `S3_*` (приватный бакет, ключ только к нему, шифрование на стороне хранилища) или резервное копирование `DATA_DIR`
- [ ] Мониторинг логов и журнала безопасности
- [ ] Регулярные обновления зависимостей
