# Архитектура Omni

## Общая схема

```
┌───────────────────────── Браузер / PWA ─────────────────────────┐
│  React 19 · react-router · TanStack Query (серверное состояние) │
│  Zustand (UI, настройки, реалтайм) · Web Crypto (E2E)            │
└──────────────┬──────────────────────────────┬───────────────────┘
               │ HTTPS REST /api/v1           │ WebSocket /api/v1/ws
┌──────────────▼──────────────────────────────▼───────────────────┐
│ Fastify 5                                                        │
│  периметр: helmet/CSP · rate limit · CSRF · сеанс из cookie      │
│  modules/*: routes (валидация zod) → service (бизнес-логика)     │
│  policy: единая точка авторизации (приватность, блокировки)      │
│  RealtimeHub: сокеты в памяти процесса                           │
└──────────────┬──────────────────────────────┬───────────────────┘
               │ node:sqlite (WAL, FTS5)      │ файлы на диске
            omni.db                        uploads/YYYY/MM/<id>.<ext>
```

## Принципы

1. **Один контракт на клиент и сервер.** `packages/shared` содержит zod-схемы входных данных, типы ответов (DTO), протокол WebSocket и лимиты. Сервер валидирует ими каждый запрос, клиент — формы. Изменили схему — TypeScript покажет все места, которые нужно поправить.
2. **Composition root.** Все сервисы создаются в `apps/server/src/context.ts` и получают зависимости через конструктор. Модули не создают друг друга сами — их легко тестировать и заменять (например, хранилище медиа на S3).
3. **Авторизация в одном месте.** `modules/policy` решает «можно ли X сделать Y»: видеть профиль, писать, комментировать, видеть «в сети». SQL-фильтр видимости ленты (`Policy.visiblePostsSql`) общий для всех лент — проверку нельзя «забыть» в новом эндпоинте.
4. **Единая модель контента.** Заметки, фото, видео и клипы — это одна таблица `posts` с полем `kind`. Лайки, комментарии, репосты, закладки, история, рекомендации и поиск работают одинаково для всех форматов. Новый формат (аудио, эфиры) добавляется без переделки остальных модулей.
5. **Навигация как данные.** `apps/web/src/app/navigation.ts` — реестр всех разделов. Из него строятся рельс, дерево, хлебные крошки, палитра Ctrl+K и мобильная шторка. Тест `navigation.test.ts` гарантирует, что в «лабиринте» нет тупиков: каждый пункт либо ведёт на маршрут, либо помечен как «скоро» с описанием.

## Сервер (`apps/server`)

| Модуль | Ответственность |
| --- | --- |
| `auth` | регистрация, вход, 2FA (TOTP, код из письма, резервные коды), подтверждение почты, восстановление пароля, сеансы, журнал безопасности, удаление аккаунта |
| `mail` | отправка писем (Brevo/Resend по HTTPS, SMTP, тестовый ящик в разработке), HTML-шаблоны |
| `users` | профили, подписки и заявки, блокировки, скрытие, настройки приватности и уведомлений |
| `policy` | централизованная авторизация |
| `chats` | личные, группы, каналы, секретные, «Избранное»; сообщения с монотонным `seq`, реакции, пересылка, закрепы, прочтение, таймеры самоуничтожения; голосовые, кружки, опросы, упоминания, медленный режим, автоудаление; свои папки (`folders`), пригласительные ссылки (`invites`), отложенные сообщения (`scheduled`), поиск по сообщениям (FTS5) |
| `calls` | звонки 1:1: состояние в БД (вызов → разговор → завершён/пропущен), сигнализация WebRTC через WebSocket только к принявшему сеансу, таймаут вызова, сообщение о звонке в чате |
| `keys` | каталог публичных ключей устройств (E2E) |
| `posts` | публикации всех видов, ленты и ранжирование, комментарии, лайки и «кто оценил», закладки, история, плейлисты, хэштеги, студия, закреп в профиле, уведомления подписчикам с «колокольчиком» |
| `social` | черновики и отложенные публикации, списки авторов, коллекции закладок, скрытые слова (фильтр лент через FTS5) |
| `media` | загрузка (проверка типа по содержимому, лимиты), подписанные ссылки, раздача с Range |
| `stories` | истории (аудитория «все»/«близкие друзья»), реакции, просмотры, архив, «Актуальное» |
| `communities`, `notifications`, `search`, `reports` | соответствующие функции |
| `realtime` | WebSocket-хаб, присутствие, «печатает…/записывает…», доставка сигналов звонка в конкретный сеанс |

**Данные.** SQLite через встроенный `node:sqlite`: WAL, внешние ключи, FTS5 для поиска. Идентификаторы — ULID (сортируются по времени, не угадываются). Время — миллисекунды UTC. Миграции — в `db/migrations.ts`, применяются при старте; опубликованные миграции не редактируются, только добавляются новые. Весь SQL параметризован; обёртка `Db` отбрасывает лишние параметры и требует отсутствующие.

**Доставка сообщений.** Сообщение сохраняется в транзакции, получая следующий `seq` чата, затем рассылается участникам через `RealtimeHub`. Отправка идемпотентна: повтор с тем же `clientId` (плохая мобильная сеть) вернёт уже созданное сообщение. После переподключения клиент перезапрашивает список чатов и открытую переписку.

**Миграции.** `001_init` — базовая схема; `002_email` — почта, коды и знакомство; `003_messenger` — голосовые, опросы, звонки, папки, приглашения, отложенные сообщения, поиск по сообщениям; `004_social` — аудитория и реакции историй, «Близкие друзья», «Актуальное», статус/ссылки/закреп профиля, черновики, списки, коллекции, скрытые слова, «колокольчик».

**Фоновые задачи** (`jobs.ts`): удаление сообщений с истёкшим таймером, отправка отложенных сообщений (каждые 10 с) и публикация отложенных постов (каждые 30 с), очистка сеансов, удалённых историй, кодов из писем и незавершённых входов, `PRAGMA optimize`.

## Клиент (`apps/web`)

- `app/` — оболочка (`layout/`), реестр навигации, маршруты (каждый модуль — отдельный чанк), сессия, обработка событий реального времени.
- `features/*` — модули разделов: `home` (сводка), `chats`, `calls` (экран звонка и история), `stories`, `feed`, `posts`, `social` (черновики, списки, коллекции, скрытые слова), `video`, `shorts`, `photos`, `communities`, `explore`, `notifications`, `profile`, `settings`, `onboarding`. Модули используют друг друга только через публичные компоненты (полоса историй, карточка поста, окна выбора).
- `shared/` — API-клиент (CSRF, ошибки, загрузка с прогрессом), UI-кит, хуки, сторы, E2E-криптография, подготовка медиа (сжатие фото с удалением EXIF, обложки видео).

**Состояние.** Серверные данные — TanStack Query; оптимистичные обновления (лайки, отправка сообщений, реакции на истории) сразу отражаются во всех закэшированных местах и откатываются при ошибке. Настройки устройства (тема, палитра, шрифт, скругления, обои, звуки, «Не беспокоить», стартовая страница, код-пароль) — Zustand с `persist`; визуальные применяются атрибутами `data-*` на `<html>`, которые переопределяют CSS-переменные из `styles/tokens.css`.

**Звонки.** `shared/calls/engine.ts` — конечный автомат звонка (исходящий → входящий → соединение → разговор → завершён) поверх `RTCPeerConnection`; экран звонка смонтирован в оболочке и живёт поверх любых страниц.

**Звуки.** Короткие сигналы синтезируются WebAudio (`shared/lib/sounds.ts`) — без аудиофайлов; учитывают громкость, тихие часы и системные уведомления при скрытой вкладке.

**Мобильность.** Брейкпоинты: телефон (< 768 px) — нижние вкладки и шторка; планшет — рельс + выезжающее дерево; десктоп — рельс + дерево + контент (+ инфо-панель чата на широких экранах). Учитываются `safe-area`, `100dvh`, шрифт ≥ 16 px в полях ввода на iOS, длинное нажатие вместо правого клика. Service Worker кэширует только оболочку приложения — личные данные API в общий кэш не попадают.

## Как масштабировать дальше

| Узкое место | Решение, под которое уже готова архитектура |
| --- | --- |
| Одна SQLite | Перенести SQL репозиториев на PostgreSQL: слой `Db` изолирован, запросы стандартные; FTS5 → `tsvector` |
| Один процесс WebSocket | Реализовать `RealtimeHub.sendToUser/sendToUsers` поверх Redis Pub/Sub или NATS — клиент не меняется |
| Файлы на диске | Подменить `MediaService.store/filePath` на S3-совместимое хранилище; ссылки уже подписанные и истекающие — подходят для CDN |
| Ранжирование ленты | Вынести `SCORE_SQL` в отдельный сервис рекомендаций с сигналами просмотров |
| Тяжёлые фоновые задачи | Очередь (BullMQ/NATS JetStream) для транскодирования видео, превью, рассылки push |
